## 1. Milestone Purpose, Scope & Architectural Boundaries

### 1.1 Purpose
Introduce an offline, high-performance, dictionary-backed **Lexicon & Writing Assistance Engine** into the shared Rust core (`crates/borno-core/src/dictionary/`), providing:
1. An in-memory, compact prefix trie with mathematically admissible branch-and-bound pruning for instant Bangla word completion.
2. A frequency-weighted Bangla vocabulary with verified provenance and permissive open-source licensing (Leipzig Corpora Collection CC BY 4.0 cross-validated with Hunspell-bn orthography).
3. A deterministic **Phonetic Ambiguity Resolution Pipeline** that generates secondary candidates for common homophone variations (e.g. `khoma` $\rightarrow$ `"ক্ষমা"`, `biggan` $\rightarrow$ `"বিজ্ঞান"`, `bhasha` $\rightarrow$ `"ভাষা"`) without changing Candidate 0.
4. Bounded orthographic spelling suggestions for typed tokens that have zero completions, using UAX #29 extended grapheme clusters and strict search budgets.
5. Backward-safe configuration schema evolution from `1.0.0` to `1.1.0` with safe runtime defaults, disk migration, and locked preservation of unknown future versions.
6. A candidate metadata architecture distinguishing Rust source API evolution, JSON serialization, and C-ABI compatibility, preserving existing public candidate strings while delivering candidate-origin information to the Desktop Sandbox UI.
7. Reproducible performance benchmarks with explicit reference environments and hard acceptance gates.

## 3. Configuration Schema Evolution (1.0.0 -> 1.1.0)

### 3.1 Policy & Compatibility Contract
M6 adopts an explicit, backward-safe migration policy:
1. **M6 writes Schema `1.1.0`:** Fresh defaults and saves in M6 write `"schema_version": "1.1.0"`.
2. **Backward-Safe Migration of `1.0.0` Configurations:**
   - Existing `1.0.0` files are parsed with standard serde field defaults for all newly added M6 fields.
   - Loaded configuration is upgraded in-memory to `"1.1.0"` and written back to disk via `save_config_safe`, respecting existing atomic-save and sync guarantees.
3. **Protection of Unsupported/Future Versions:**
   - Any version other than `"1.0.0"` and `"1.1.0"` (e.g. `"1.2.0"` or `"2.0.0"`) is preserved byte-for-byte untouched on disk.
   - Persistence status is set to `PersistenceStatus::LockedUnsupportedVersion { version }`. Ordinary save calls are rejected to prevent clobbering future features.
4. **Older M5 Build Protection:**
   - An older M5 build reads `raw_val.get("schema_version")`.
   - Encountering `"1.1.0"`, the M5 binary sees `version_str != "1.0.0"`, immediately treats it as `UnsupportedVersionPreserved`, and locks persistence without modifying or saving over the `1.1.0` file. New settings cannot be silently discarded.

## 4. Candidate Metadata Architecture & Compatibility Across Boundaries

### 4.1 Boundary Analysis: Rust Source, JSON, and C-ABI
Compatibility must be explicitly distinguished across the three distinct consumer boundaries:

1. **Rust Source API Boundary:**
   - `EngineState` in `crates/borno-core/src/lib.rs` currently has all public fields.
   - Adding `pub candidate_details: Vec<CandidateDetail>` directly to `EngineState` is an **intentional public API expansion** (minor version evolution). Any external code that constructed `EngineState` via struct literal without `..Default::default()` would fail to compile.
   - An audit of the workspace reveals that no external crate or integration test uses struct literal syntax to instantiate `EngineState` (they all call `BornoEngine::new().state()` or `engine.process_event()`).
   - To preserve backward-friendly Rust ergonomics while acknowledging the expansion, `impl Default for EngineState` initializes `candidate_details: Vec::new()`.

2. **JSON Serialization & Deserialization Boundary:**
   - Tauri serializes `ProcessResult.state` into JSON sent across IPC to the React frontend.
   - React interface in `src/types.ts` is updated to include `candidate_details?: CandidateDetail[]`.
   - **Deserialization Invariant Resolution:** If legacy JSON lacking `"candidate_details"` is deserialized by M6, a post-deserialization hook or serde custom deserializer populates `candidate_details` by mapping `candidates` into `CandidateDetail { text: s.clone(), kind: CandidateKind::PrimaryTransliteration, score: 0 }`. This ensures the 1-to-1 lockstep invariant is NEVER violated:
     $$\text{candidates.len()} \equiv \text{candidate\_details.len()}$$
     $$\forall i < \text{candidates.len()},\; \text{candidates}[i] == \text{candidate\_details}[i].\text{text}$$

3. **C-ABI Boundary:**
   - The memory layout of `BornoStateC` in `borno.h` is **STRICTLY UNTOUCHED**:

   - No fields are added to `BornoStateC`, ensuring existing binary callers and FFI tests do not experience struct size or alignment changes.
   - To query candidate kind in C, a non-breaking accessor function querying the active engine handle is added:

     Returns `0`: Primary, `1`: PhoneticAlt, `2`: ExactMatch, `3`: Completion, `4`: Correction, `-1`: Out of bounds / invalid.

## 5. Phonetic Ambiguity Resolution Pipeline

### 5.1 The Root Cause of Phonetic Ambiguity
Avro phonetic transliteration in M3 operates via greedy longest-prefix pattern matching over ASCII inputs. By design, deterministic rule-based transliteration cannot distinguish homophonic or etymological spelling variations from Latin characters alone:
- Latin `khoma` produces rule output `"খমা"`. The target word is `"ক্ষমা"` (typed `kShoma` or `xoma`).
- Latin `biggan` produces rule output `"বিগ্গান"`. The target word is `"বিজ্ঞান"` (typed `bijNGan` or `bijgyan`).
- Latin `bhasha` produces rule output `"ভাশা"`. The target word is `"ভাষা"` (typed `bhaSha`).

A Bengali prefix trie alone cannot resolve this because the target words begin with different Bengali Unicode roots (`ক্ষ` begins with `ক` U+0995, not `খ` U+0996; `জ্ঞ` begins with `জ` U+099C, not `গ` U+0997; `ষ` is U+09B7, not `শ` U+09B6).

### 5.2 Deterministic Ambiguity Pipeline & Precedence
M6 introduces an explicit **Lexicon-Validated Phonetic Ambiguity Pipeline** in `crates/borno-core/src/dictionary/ambiguity.rs`:

```
[Raw Latin Buffer: "khoma"]
            │
            ▼
[PhoneticEngine::transliterate]
  ├── Primary: "খমা" (Slot 0 Invariant)
  └── M3 Rule Alternates: []
            │
            ▼
[PhoneticAmbiguityMap::generate_variants]
  Applies ordered homophone rewrite rules to raw buffer:
  1. Word-initial "kh" -> "kSh"  => "kShoma"
  2. Medial "gg" -> "jNG"
  3. Medial "sh" -> "Sh"
  Cap: At most 2 variant rewrites generated
            │
            ▼
[PhoneticEngine::transliterate(variant)]
  Transliterates "kShoma" -> "ক্ষমা"
            │
            ▼
[Lexicon Trie Lookup: trie.contains("ক্ষমা")]
  ├── If TRUE in Lexicon: Elevate "ক্ষমা" to Candidate 1 (Kind: ExactLexiconMatch)
  └── If FALSE / Missing: Discard variant (Zero unverified hallucinated candidates)
```

### 5.3 Curated & Versioned Ambiguity Rules
```rust
pub struct AmbiguityRule {
    pub pattern: &'static str,
    pub replace_with: &'static str,
    pub condition: AmbiguityCondition,
}

pub enum AmbiguityCondition {
    WordInitial,
    Medial,
    Anywhere,
}

pub static PHONETIC_AMBIGUITY_RULES: &[AmbiguityRule] = &[
    // 1. Initial Kh -> Ksh (e.g. khoma -> kShoma -> ক্ষমা)
    AmbiguityRule { pattern: "kh", replace_with: "kSh", condition: AmbiguityCondition::WordInitial },
    // 2. Medial gg -> jNG (e.g. biggan -> bijNGan -> বিজ্ঞান)
    AmbiguityRule { pattern: "gg", replace_with: "jNG", condition: AmbiguityCondition::Medial },
    // 3. Medial sh -> Sh (e.g. bhasha -> bhaSha -> ভাষা)
    AmbiguityRule { pattern: "sh", replace_with: "Sh", condition: AmbiguityCondition::Medial },
    // 4. Sibilant triads
    AmbiguityRule { pattern: "s", replace_with: "Sh", condition: AmbiguityCondition::Anywhere },
];
```

### 5.4 Exact Operational Invariants & Verification Status
1. **Rule Precedence:** Evaluated strictly in order of definition in `PHONETIC_AMBIGUITY_RULES`.
2. **Variant Generation Limit:** At most **2 candidate variants** are generated per token, preventing combinatorial explosion.
3. **Lexicon Validation Gate:** Every generated variant must return `true` from `trie.contains(&target)`. If the target word is absent from the ingested lexicon, the variant is silently discarded.
4. **Preservation of Candidate 0:** Candidate 0 is ALWAYS the primary transliteration. The ambiguity match occupies Slot 1.
5. **Deduplication:** Variants identical to Candidate 0 after NFC normalization are discarded.
6. **Explicit Verification Status:**
   - Transliterations of the raw buffer (`khoma` $\rightarrow$ `"খমা"`, `biggan` $\rightarrow$ `"বিগ্গান"`, `bhasha` $\rightarrow$ `"ভাশা"`) and rewritten buffers (`kShoma` $\rightarrow$ `"ক্ষমা"`, `bijNGan` $\rightarrow$ `"বিজ্ঞান"`, `bhaSha` $\rightarrow$ `"ভাষা"`) are **VERIFIED** by repository tests (`phonetic_tests.rs:L420-L432`).
   - The secondary suggestion behavior (`khoma` offering `"ক্ষমা"` in Slot 1) is a **PROPOSED M6 FEATURE** that remains **UNVERIFIED until M6 implementation and lexicon ingestion**.

## 6. Bengali Grapheme Boundaries & Completion Eligibility

### 6.1 Verified UAX #29 Grapheme Cluster Facts (from Repository Tests)
Testing `crates/borno-core/src/unicode.rs` and `tests/unicode_golden_tests.rs` (lines 255–276) establishes the following ground truth under the existing `unicode-segmentation = "1.13.3"` dependency:

| Input Text | Unicode Code Points | Extended Grapheme Clusters (UAX #29) | Grapheme Count | Explanation |
|---|---|---|---|---|
| `"ব"` | U+09AC | `["ব"]` | **1** | Single base consonant. |
| `"বা"` | U+09AC, U+09BE | `["বা"]` | **1** | Dependent vowel sign bonds to base (Rule GB9). |
| `"বাং"` | U+09AC, U+09BE, U+0982 | `["বাং"]` | **1** | Anusvara (U+0982) is `SpacingMark` (Rule GB9a), bonding into the preceding syllable cluster! |
| `"বাংলা"` | U+09AC, U+09BE, U+0982, U+09B2, U+09BE | `["বাং", "লা"]` | **2** | Two distinct syllable clusters. |
| `"বাংলাদেশ"` | 8 code points | `["বাং", "লা", "দে", "শ"]` | **4** | Four extended grapheme clusters. |
| `"ক্ষ"` | U+0995, U+09CD, U+09B7 | `["ক্ষ"]` | **1** | Virama/hasanta bonds consonant cluster into 1 grapheme. |
| `"ক্ষমা"` | 4 code points | `["ক্ষ", "মা"]` | **2** | Conjunct + Consonant with Kar. |

### 6.2 Grounded Completion Eligibility Rules
Because `"বাং"` is 1 extended grapheme cluster under UAX #29, completion eligibility must NOT be gated on `grapheme_count >= 2`.

Prefix word completion is eligible if and only if:
1. `enable_dictionary_assistance == true` AND `enable_word_completion == true`.
2. **Preedit Character / Code Point Count $\ge 2$** OR **Raw Latin Buffer Length $\ge 2$** (e.g. `"ba"` $\rightarrow$ `"বা"`, `"bang"` $\rightarrow$ `"বাং"`).
3. **Single Consonant Invariant:** A single isolated consonant without vowels or modifiers (e.g. `"ব"`, code point count 1) does **NOT** trigger prefix completions. This prevents candidate window flooding on the first letter typed.

## 7. Bounded Search, Typo Correction & Pruning Guarantees

### 7.1 Unambiguous Typing & Correction Lifecycle
To prevent premature typo suggestions from polluting the candidate window while a user is typing a valid word:

```
                  [User Keystroke in Phonetic Mode]
                                 │
                                 ▼
                     [Preedit Token Generated]
                                 │
                 ┌───────────────┴───────────────┐
                 │                               │
       [Completions Count > 0]         [Completions Count == 0]
                 │                               │
                 ▼                               ▼
       [Show Word Completions]           [Is Preedit chars >= 3?]
       [Spelling Correction: OFF]        ├── YES: Run Bounded Typo Search
                                         └── NO:  Zero Corrections (Keep Typing)
```

1. **Valid Incomplete Prefix:**
   - If `predict_completions(prefix)` finds $\ge 1$ completions in the trie, **spelling correction is strictly suppressed (0 typo corrections)**.
   - Even if completions return fewer results than `max_dictionary_suggestions`, typo search does NOT run. The user is actively typing a valid prefix.
2. **Exact Lexicon Word:**
   - If `trie.contains(preedit) == true`, Candidate 0 is the exact word. Prefix completions extending this word may appear in secondary slots. Spelling correction is **suppressed**.
3. **Token Eligible for Spelling Correction:**
   - Spelling correction is triggered if and only if:
     1. Preedit character count $\ge 3$ (and grapheme count $\ge 2$).
     2. `trie.contains(preedit) == false` (not an exact word).
     3. `predict_completions(preedit)` yields **0 completions** (dead end in trie).
4. **Empty or Missing Lexicon:**
   - If dictionary resources are unavailable, completions and corrections return empty `Vec`. Engine seamlessly falls back to pure M3 candidate generation with zero errors or panics.
5. **Zero Automatic Commits:**
   - Secondary suggestions (completions, corrections, ambiguity matches) are **never committed automatically**. They require explicit user selection.

### 7.2 Mathematically Admissible Trie Pruning
Candidates in prefix completion are totally ordered by the key tuple:
$$K(w) = (\text{frequency}(w) \downarrow, \text{grapheme\_length}(w) \uparrow, \text{unicode\_codepoint}(w) \uparrow)$$
- Higher frequency is strictly better.
- For equal frequencies, shorter word length is strictly better.
- For equal frequency and length, lexicographical Unicode order breaks ties deterministically.

#### Admissible Subtree Upper Bound
Every trie node $u$ stores `max_subtree_frequency: u32`, which is the maximum frequency of any terminal word in the subtree rooted at $u$.
Let $w_{\min}$ be the lowest-ranked candidate currently in the top-$M$ priority queue of discovered completions.
- **Pruning Rule:** A subtree rooted at child node $v$ can be pruned if and only if:
  $$\text{max\_subtree\_frequency}(v) < \text{frequency}(w_{\min})$$
- If $\text{max\_subtree\_frequency}(v) == \text{frequency}(w_{\min})$, the subtree **MUST NOT be pruned**, because it may contain an equal-frequency candidate with shorter length or smaller lexicographical code point that beats $w_{\min}$.
- This bound is provably admissible and guarantees that the true top-$M$ candidates are never missed.

### 7.3 Bounded Approximate Search (Spelling Correction)
- **Distance Metric:** Damerau-Levenshtein computed strictly over UAX #29 extended grapheme clusters using `unicode::grapheme_indices`.
- **Search Bounds:**
  - Maximum edit distance: $D = 1$ for tokens with 3 to 5 characters; $D \le 2$ for tokens with $\ge 6$ characters.
  - **Node Budget:** Hard cap `MAX_VISITED_NODES = 1,000`. If DFS traversal visits 1,000 nodes without finding closer matches, the search halts and returns the best candidates found so far.
  - Pruning via Dynamic Programming row: if $\min(\text{row}) > D$, the entire subtree is immediately pruned.

## 8. Candidate Limits, Ranking Policy & Lockstep Slicing

### 8.1 Interaction of Limits
- `candidate_display_limit` ($K$, default 5, range 1..=9): Total maximum presentation candidates in UI.
- `max_dictionary_suggestions` ($M$, default 3, range 1..=5): Maximum candidates originating specifically from dictionary operations (ambiguity matches, prefix completions, typo corrections).
- `enable_dictionary_assistance` (bool, default true): Master toggle. If false, zero dictionary candidates are admitted.
- `enable_word_completion` (bool, default true): Sub-toggle. If false, prefix completions are suppressed; ambiguity matches and typo corrections remain eligible.

### 8.2 Unified Ranking & Slicing Order
Given display limit $K$ and dictionary limit $M$:

```
┌────────────────────────────────────────────────────────────────────────┐
│ Slot 0: Primary Transliteration (INVARIANT: Raw user intent preserved) │
├────────────────────────────────────────────────────────────────────────┤
│ Slot 1..K-1: Merged Secondary Candidates (up to M dictionary items)     │
│  1. Phonetic Ambiguity Matches (verified in lexicon) [dict]            │
│  2. M3 Phonetic Alternates (ALT-1 high-vowels, ALT-2 sibilants)        │
│  3. Prefix Word Completions (sorted by freq desc, length asc) [dict]   │
│  4. Spelling Corrections (sorted by dist asc, freq desc) [dict]        │
└────────────────────────────────────────────────────────────────────────┘
```

1. **Slot 0:** Primary transliteration is placed at index 0. It does NOT count toward $M$.
2. **Merging & Counting:** Secondary candidates are merged in priority order. Each candidate with kind `ExactLexiconMatch`, `PrefixCompletion`, or `SpellingCorrection` increments the dictionary count. Once the dictionary count reaches $M$, subsequent dictionary candidates are rejected. Non-dictionary M3 phonetic alternates do not count toward $M$.
3. **Lockstep Slicing:** The total candidate list is sliced to $\min(K, \text{candidates.len()})$. Slicing is applied synchronously to `candidates` and `candidate_details`, guaranteeing index alignment.
4. **Single-Candidate Case ($K = 1$):** Only Candidate 0 is returned (`candidates.len() == 1`). Secondary dictionary suggestions cannot be displayed.

  - **Strict Boundary:** Hunspell-bn is used strictly as an **offline verification oracle** during data preprocessing (`scripts/prepare_lexicon.py`) to confirm the orthographic validity of Leipzig words. **No Hunspell-bn data is copied or redistributed into the runtime binary.** All distributed lexicon entries and frequency scores originate exclusively from the CC BY 4.0 Leipzig corpus.
- **Licensing Stop Condition:** If during data preparation any required source artifact cannot be verified under CC BY 4.0 or compatible permissive redistribution terms, implementation MUST halt.

### 9.2 Reproducible Preprocessing Pipeline (`scripts/prepare_lexicon.py`)
1. **Ingest Raw Corpus:** Reads Leipzig `*-words.txt` containing word tokens and observed raw frequencies.
2. **Unicode Normalization (UAX #15):** Normalizes every word to standard NFC (`normalize_nfc`).
3. **Character Filter & Script Validation:**
   - Retains only words composed strictly of assigned Bengali Unicode code points (U+0980..=U+09FF) and valid joiners (ZWJ U+200D, ZWNJ U+200C).
   - Discards ASCII, digits, punctuation, and unassigned code points.
   - Legitimate loanwords and foreign names written in Bengali script (e.g. `"কম্পিউটার"`, `"বাংলাদেশ"`) are fully preserved.
4. **Deduplication & Frequency Aggregation:**
   - Multiple raw tokens that collapse to the same NFC representation have their frequency counts summed.
5. **Vocabulary Curation:**
   - Filters out extreme hapax legomena (frequency count < 3).
   - Retains the top 30,000 to 50,000 most frequent unique words.
6. **Provenance Manifest:**
   - Emits `docs/lexicon_provenance.json` recording source URL, commit/date, raw line count, NFC deduplication count, retained word count, and sha256 checksum.

### 9.3 Packaging Strategy: Compile-Time Embedded Lexicon
M6 adopts **Compile-Time Embedded Static Data** in `borno-core` (via `include_bytes!` or generated static table):
- **Rationale:**
  - `borno-core` is a shared Rust library consumed by desktop Tauri, C-ABI FFI, and native platforms (TSF in M7).
  - Dynamic file loading requires runtime path resolution, permissions, and packaging hooks in Tauri that fail in headless test runners or FFI harnesses.
  - An embedded binary format compiles directly into the core binary, guaranteeing **100% offline reliability with zero runtime file path lookups**.
- **Footprint Impact:**
  - 35,000 words compressed via compact trie representation occupies ~2.0–3.0 MB.
  - Easily satisfies the binary size overhead limits.

## 14. Stop Conditions & Governance Rules

The agent must halt and immediately report to the developer if:
1. **License Conflict or Ambiguity:** Any candidate dataset lacks clear redistribution rights under CC BY 4.0, MPL 1.1, or Apache-2.0 / MIT compatible terms.
2. **Candidate Contract Breakage:** Any change that modifies `candidates: Vec<String>` or breaks C-ABI `BornoStateC` or `contract_tests.rs`.
3. **Candidate Hijacking:** Any ranking logic that replaces Slot 0 (primary transliteration) or commits text without explicit user selection.
4. **Performance Gate Failure:** End-to-end p95 keystroke latency exceeds $1.0\text{ ms}$ under release profile, or heap overhead exceeds $25\text{ MB}$.
5. **Schema Regression:** Older M5 binaries reading an M6 configuration file fail to lock or overwrite/corrupt the file.
6. **Scope Creep:** Any attempt to implement system-wide Windows TSF IME hooks (deferred to M7), custom layout authoring (deferred to M9), or contextual multi-word SLM prediction (deferred to M10).
